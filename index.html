About

Operator Upgrade Path Finder works out how an OpenShift operator gets from the version you are running to the version you want, using the operator's own OLM catalog as the source of truth.

It applies the same rules OLM itself uses when it resolves a Subscription — replaces, skips and skipRange — so the path you see is the path the cluster would actually take: every hop, the channel it runs on, and any point where the Subscription channel has to change. When no upgrade path exists, it says so and explains why.

Setup — building the catalog source

This page reads an OLM file-based catalog that you extract from the Red Hat operator index image. Clone the repository, pull the catalog, build the index, then serve the page — opening the firewall port only if you need to reach it from another machine.

  1. Get the application

    Clone the repository and move into it — every command below runs from there.

    git clone https://github.com/QikfixAI/ocp_operator_upgrade_path_finder.git
cd ocp_operator_upgrade_path_finder

  2. Extract the catalog from the operator index

    The index image carries every operator's catalog under /configs, one sub-directory per operator. Match the tag to your cluster's OpenShift version (v4.14, v4.16, v4.19…).

    podman login registry.redhat.io -u REDHAT_USER_HERE
podman pull registry.redhat.io/redhat/redhat-operator-index:v4.16
podman create --name rhoai-catalog registry.redhat.io/redhat/redhat-operator-index:v4.16
podman cp rhoai-catalog:/configs /tmp/catalog
podman rm rhoai-catalog

    Then put it next to this page, as catalog/:

    mv /tmp/catalog ./catalog

    Expect roughly 1.5–2 GB. Individual catalog.json files run to 200 MB+ because they embed every bundle's manifests as base64.

  3. Build the index

    build-index.sh walks each sub-directory of catalog/ and distils it down to just the upgrade graph — the olm.package and olm.channel records. The olm.bundle records are the bulk of the bytes and hold nothing the upgrade path needs, so they are streamed past and discarded.

    ./build-index.sh catalog data

    This writes data/operators.json plus one small file per operator, turning ~1.6 GB into ~1 MB in a few seconds. It handles every layout in the index image: catalog.json, index.json, channels/*.json, channel.json and the YAML variants.

    Needs python3 (used by default) or jq (--engine jq; JSON layouts only). Re-run it whenever you pull a newer catalog.

    It also regenerates version.js from version.conf, which is what lets the footer show a version when this page is opened straight from disk. After bumping version.conf you can refresh just that, without reindexing:

    ./build-index.sh --version-only

  4. Open the port on the firewall (RHEL)

    Only needed if you will reach the page from another machine. Skip it if you are browsing from the same host that runs the server.

    sudo firewall-cmd --permanent --add-port=8000/tcp
sudo firewall-cmd --reload

    --permanent writes the rule to the zone config so it survives reboots, but does not touch the running firewall — that is what --reload is for. Confirm with sudo firewall-cmd --list-ports. Drop sudo if you are already root.

    Opening the port exposes the whole directory, catalog included, to anyone who can reach the host — the server has no authentication. On a shared or internet-facing machine, prefer --bind 127.0.0.1 plus an SSH tunnel (ssh -L 8000:localhost:8000 user@host).

  5. Serve the page

    Browsers block fetch() on file:// URLs, so the page has to be served over HTTP. From this directory:

    python3 -m http.server 8000

    Then open it and pick an operator — either way works:

    • On this machine — http://localhost:8000/
    • From another machine, if you installed this on a remote host — http://<server-ip>:8000/. The server already listens on every interface, so you only need the port open (step 4). Find the address with hostname -I or ip -4 addr show.

    Without data/ the page still works: it discovers operators from the web server's directory listing of catalog/ and stream-parses the catalog you select. That re-reads the full file each time — several seconds for the largest ones — which is why step 3 is worth running.
